## Current ownership and execution path

1. `apps/chat/lib/app-chat-runtime.ts:100` creates an application runtime with a store and `ApplicationThread`, keyed by parsed chat/runtime identity. `apps/chat/lib/application-thread.ts:5` merely specializes `AbstractThread<ChatMessage>`. The registry and runtime controller own lifetime separately from the layout. Preserve this distinction when swapping execution backends: mounting another view must not create another generation.
2. `apps/chat/components/chat-sync.tsx:57` composes a gated transport, cancellation-aware transport and AI SDK `DefaultChatTransport`. Authenticated send transmits the latest user message and no client history; anonymous send transmits previous UI messages (`:68`). Resume uses chat ID plus the selected partial assistant ID (`:78`). The hook routes completion, transient persistence acknowledgments and errors into local state (`:95–143`). Its last-message resume targeting is current implementation, not proof that every parallel run reconnects after reload.
3. `packages/thread/src/abstract-thread.ts:243` implements regeneration as a new sibling run, not replacement of the previous assistant. `:143` routes approval response by approval ID, `:149` tool output by tool-call identity. `packages/thread/src/ai-sdk-run-chat.ts:1` imports public `AbstractChat`, `ChatState` and `ChatTransport` from AI SDK; one run owns its own message path and status. Tree storage, cursor selection and run execution are interwoven in AbstractThread but the tree implementation is separate.
4. `apps/chat/app/(chat)/api/chat/route.ts:1106` authenticates/validates, resolves inputs and streams. Chat ownership and cross-chat message rejection occur at `:172–230`. The server reads stored messages to the requested parent using `get-thread-up-to-message-id.ts:4–14`. `route.ts:760–791` truncates selected previous context to five messages. `lib/ai/core-chat-agent.ts:49–67` again selects the last five, filters reasoning, drops custom data parts on `convertToModelMessages`, and materializes file URLs as binary content. Therefore the UI transcript is NOT the exact model input, and saving only rendered text or model output is insufficient for faithful divergent continuation.
5. `core-chat-agent.ts:69–125` obtains model/provider options, tools and per-user MCP clients. `:131–168` directly runs `streamText` with `instructions`, a five-step stop plus deep-research-report termination, transforms, telemetry, abort signal and cleanup. Eve should replace the principal durable orchestration loop; model resolution, tool policy and provider adapters survive.
6. `route.ts:355–502` creates AI SDK UI stream events, merges result output, attaches metadata/usage, streams followups and finalizes persisted output/credits. `:561–641` reserves an assistant placeholder, detects pre-start cancellation and checks DB cancellation at most once per second on chunks. `:71–100,668–679` uses Redis/resumable-stream with Next `after`; this is resumable delivery around a request-owned computation, not durable workflow replay.
7. `api/chat/[id]/stream/route.ts:35–102` checks message/chat membership and private chat ownership (public chats permit reads), then resumes a Redis stream or emits a finalized `data-appendMessage`. Missing live stream without finalized output returns 204. Durable Eve recovery must replace this gap with an explicit committed/pending/failed state.

**Before/after example (proposal):** Today editing user U1 creates a sibling in ChatJS's tree and sends its selected ancestry through the HTTP agent route. With Eve, ChatJS authorizes the owner and ancestry, resolves the exact canonical model history for that branch, creates a new Eve execution session for the divergent path and records its durable binding. Merely changing the UI cursor does not alter Eve's history. Continuing the same linear leaf can reuse its session when the canonical execution contract permits it. Concurrent siblings require separate session/operation identities and independent cancel/approval targets.

## Persistence and safe retirement boundaries

Current tables in `lib/db/schema.ts:81–229` store Chat metadata, Message ancestry/model/parallel/stream/cancel state and normalized Part rows (text/reasoning/files/sources/tools/data). This is application UI history, not guaranteed full provider/canonical execution history. Document (`:253`), Suggestion (`:282`), Vote (`:231`), auth (`:307` onward), credits/preferences/projects and MCP ownership are separate feature data; they must not be wiped with the execution store.

Prefer one durable authoritative record for a canonical turn, with app ancestry/binding rows referencing it; derive display projection where lossless enough for UI. Do not plan simultaneous writable old Message/Part canonical history and Eve canonical history. If exact canonical history cannot be obtained from the selected Eve storage/API, the patch/fork decision is a prerequisite for branching—not a reason to use transient SSE as a second canonical ledger.

Retire only after the corresponding feature/acceptance gate passes:

- Principal `api/chat/route.ts` streaming implementation and `api/chat/[id]/stream/route.ts` Redis reconnect implementation. Preserve/extract authentication, quota/model policy, title/instructions, tool policy, cancellation identity and accounting before deleting orchestration.
- `lib/ai/core-chat-agent.ts` principal loop; retain concrete context preparation/provider/tool logic in the new execution composition.
- `lib/cancellation-aware-chat-transport.ts`, `lib/gated-chat-transport.ts`, completion queue/append-message reconciliation and `components/chat-sync.tsx` current transport: replace by one Eve synchronization owner, preserve provisional persistence acknowledgment/parallel dispatch semantics.
- `packages/thread/src/ai-sdk-run-chat.ts` and execution-specific sections of AbstractThread/run registry. Retain tree ancestry algorithms, branch selections and useful controlled tree tests under a deliberate exported API. Do not delete the package simply because Eve has sessions.
- Stream-specific metadata/columns (`activeStreamId`, `canceledAt`, GenerationCancellation) and message/part writer paths only after new schema/binding references, completed-run projection and the approved fresh-store/old-release rollback treatment are decided. Migration planning must not drop shared tables or old data.
- Redis/resumable-stream dependencies only after import/env inventory confirms no remaining anonymous rate-limit/cache/other use; route currently shares Redis for anonymous rate limits. Removing stream recovery does not authorize removing rate limits.
- Remove old tests only when equivalent behavior is exercised against the new execution boundary; keep tree/parallel/cancellation regression cases and package export/cache smoke tests. No compatibility aliases or permanently dormant old engine exports in the final supported runtime.
