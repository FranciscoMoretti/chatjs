# Existing ChatJS → Eve: persistence, authorization and cutover plan

Planning only, 2026-09-07. Initial source inspected at `2db364c2c149b60e1180858bfe2c795329122dc9` (includes #317/#327 UI and #329 cache); refreshed through latest main `5b6664e7b846851228605933160281b07a4b0ce2`, which adds #332 gateway registry selection. The additive gateway delta is recorded below. No app implementation, database mutation, deployment or legacy deletion is proposed for this research turn.

## Recommendation and decision basis

Migrate the existing `apps/chat` execution engine behind its ChatJS-owned conversation/tree and application APIs. Preserve the resolved default demo features. Keep application metadata and ownership durable in PostgreSQL, Eve execution/history durable in its selected World, and file bytes with the selected Files SDK provider. Prefer one authoritative committed structured-history record in Eve; application projections reference it and are rebuildable. A single physical database server is possible; shared table ownership or a second independently writable transcript is not.

Use the already approved **fresh conversation store cutover**. Do not make historical conversation conversion a prerequisite: [#292's resolution](https://github.com/FranciscoMoretti/chat-js/issues/292) expressly permits a fresh store, preserves the old export/release/data, and excludes transferring in-flight work or converting new Eve data back on rollback. This is different from preserving new conversations' branching, which remains mandatory under [#286](https://github.com/FranciscoMoretti/chat-js/issues/286). [#290](https://github.com/FranciscoMoretti/chat-js/issues/290) retains PostgreSQL-first portability, Files SDK, tRPC, app-supplied identity and optional services. The current instruction explicitly permits considering Eve patches/forks; the older upstream-first preference is not a prohibition.

This report uses the research and strategic-testing skills: reuse existing primary-source proofs; plan tests for security/persistence/recovery invariants, not tests of this Markdown document. No runtime or new infrastructure proof was executed here.

### Current ancestry and model context are different things

Authenticated send resolves the submitted parent through all messages of that chat using `getThreadUpToMessageId` and `buildThreadFromLeaf`. Anonymous send currently accepts client-provided prior messages. The route takes the last five prior messages; the core agent again takes five messages including the new user message, filters reasoning, adds explicit tool requests, converts with AI SDK `convertToModelMessages`, drops `data-*`, and downloads file URLs into binary model inputs. Current `lastContext` is not evidence of an exact full committed execution-history store: query mapping also uses that column as usage metadata. Do not treat it as an Eve canonical-history import.

The tree helper's 100-iteration cap and recovery of missing/cyclic parents are current defensive display behavior; a new server history resolver must fail closed for invalid execution ancestry and avoid silently truncating a valid long tree at this incidental limit. UI fallback recovery does not grant authority to execute malformed parent paths.

Sources: [route prepareRequestContext](https://github.com/FranciscoMoretti/chat-js/blob/2db364c2c149b60e1180858bfe2c795329122dc9/apps/chat/app/(chat)/api/chat/route.ts), [core agent](https://github.com/FranciscoMoretti/chat-js/blob/2db364c2c149b60e1180858bfe2c795329122dc9/apps/chat/lib/ai/core-chat-agent.ts), [thread utilities](https://github.com/FranciscoMoretti/chat-js/blob/2db364c2c149b60e1180858bfe2c795329122dc9/apps/chat/lib/thread-utils.ts).

Proposal: preserve the *path choice* and all completed tool/document references; treat model context-window policy as a separate explicit Eve configuration. Do not assert that current five-message truncation is existing semantic compaction. Eve compaction must preserve original display history and bind its effective canonical memory to the exact applicable ancestor prefix. Never apply a compacted sibling's memory merely because it belongs to the same conversation.

### Authorization is more than authenticated routes

Today tRPC `protectedProcedure` verifies a Better Auth user; individual procedures check chat/project ownership. `getPublicChatMessages` intentionally reads public chats; the current stream route also permits public chat reads. The new execution mutation API must remain owner-authorized even when a conversation is public. A public display reader must not expose server-only canonical content, credentials, internal instructions or pending approval controls.

The anonymous cookie currently contains unsigned JSON and is not `httpOnly`. Its ID/credits cannot serve as a trusted Eve owner. Preserve anonymous use through a server-minted verified opaque/signed subject, with explicit expiry and account-transition policy; do not silently turn anonymous sessions public. Login state changes must clear/scope browser pending operations and projections to the new principal. Anonymous-to-account adoption needs an explicit authorized transfer if provided, not ID equality.

Known current source hazards should inform the new seam's acceptance tests without expanding this plan into unrelated cleanup: `saveDocument` reads an arbitrary document ID and appends with the current user without an owner comparison; vote mutation checks the chat but does not itself compare message.chatId; deletion is timestamp/list-position based and deletes the target and later rows, not just tree descendants. Reimplement the intended authorized tree operation, not incidental unsafe shortcuts. Do not revive #328 or #330 as prerequisites.

## Proposed persistence and execution contract

Names below describe domain responsibilities, not a new package/versioning framework or a settled SQL migration.

1. **Conversation and nodes, application-owned:** stable conversation/node IDs, trusted owner subject, parent relation, selected model/tool and parallel-slot metadata, ordinary title/pin/project/sharing data. A branch is a path; do not require a new branch table or a permanent one-to-one branch/session relation.
2. **Execution binding, application-owned:** conversation, exact authorized origin node/prefix, Eve session ID, execution/turn/node mappings, create operation ID and pending/bound/reconciliation state. A unique session binding prevents a session from being attached to two incompatible conversation/owner mappings. Namespace trusted subjects by issuer/type/id; browser-supplied tenant/owner values are untrusted.
3. **Committed canonical history, Eve-owned:** exact structured model messages after seed, model/tool result conversion, turn settlement and compaction; provenance sufficient to resolve a settled prefix at a particular execution boundary. Read only on server. Prefer storing this once durably in Eve and referencing that record from ChatJS rather than copying it into app JSON plus an Eve event. If the chosen patch/fork cannot provide a stable record/export, this is a gap to resolve explicitly, not a UI-message reconstruction fallback.
4. **Display projection, derived:** typed ChatJS messages preserve rich frontend tool results/custom data and document references using committed event facts. Projection/cursor move together; zero-cursor replay rebuilds missing projection. Do not claim rich UI payloads can be reconstructed from lossy model text. If Eve does not retain rich facts required by the current tool contract, capture them durably at the same execution fact boundary; do not let UI reducers become another author of transcript truth.
5. **Application effects, separately authoritative:** revisions, file objects/references, quota charges, connector configuration. A durable completed tool result references an existing effect; replay does not perform it again. Use narrowly scoped idempotency keys at irreversible effect boundaries. At-least-once workflow replay is not exactly-once external mutation.

For `U1 → A1 → U2 → A2`, continuing at A2 may reuse the matching session. Editing U2 creates a sibling U2′ and fresh Eve session seeded from the exact settled prefix through A1; it must not clear/reset the old session. Regenerating A1 creates a new sibling response execution from U1. Two parallel model responses to U2 have independent sessions/turn bindings and cancel targets. Selection changes do not mutate these mappings or stop either execution. A late approval always resolves against its original session/turn/input IDs, even when another path is visible. Seeding inherited completed tools never re-executes them.

Creation must authorize before coalescing, not inside the coalesced function: the prototype keyed active creates by branch + operation before checking owner and allowed another principal to join an in-flight promise. Durable reservation uniqueness is required across app replicas as well as local promise joining. Reservation payload is immutable for a valid operation; a changed payload under the same key is rejected. No timeout can prove a create did not commit in Eve. A stopped worker cannot be assumed dead solely because its request timed out.

**Required recovery result:** crash before request, during unknown delivery, after Eve commit/before binding, and after binding/before response either converges to the exact same durable canonical session or returns a documented unresolved state without a second creation. An explicit unresolved state is a safety fallback, not the full recoverable-creation feature. Whether linearizable creation belongs in Eve/World or a safely fenced app coordinator must be proved by the sibling gap audit; do not assume every application-coordination failure requires an upstream API.

## Cutover alternatives and concrete runbook

### A. Fresh new database/store, retained old deployment (recommended, already permitted)

New ChatJS app schema and new Eve World schemas start empty. Keep legacy database/object references and immutable old build intact. This is the smallest safe scope and avoids false claims about serializing unknown old tool outputs or reconstructing past provider messages.

Before implementation release: inventory tables/row counts, foreign keys, object namespaces and encrypted credential ownership without exporting secrets into logs; select retention and operator owner. Test backup/restore in disposable infrastructure with counts and representative branches/documents/files. Decide whether new accounts are fresh or explicitly copied (below). Never use `deleteChatById` as reset: it deletes attachments and cascades documents/votes.

At an independently authorized cutover: stop new old-engine sends (including tools/parallel requests), drain or explicitly cancel active requests, snapshot legacy DB + necessary object bytes/config/key references, retain old build/config; start the new version with distinct new DB/World credentials and object namespace. Route traffic only after smoke/parity gates. Old Redis queues/stream IDs/cancellation rows are never imported as resumable Eve runs. No tool, model call or approval is replayed during archival.

Rollback: stop new Eve work and explicitly drain/cancel per operational policy; snapshot new app/World/object state and retain compatible build. Restore routing to old build+old data. New conversations remain in preserved Eve data and are unavailable in old UI; no reverse conversion is promised. Subsequent forward recovery reconnects only with its matching stores/build. Repointing old code at the new schema is not rollback.

### B. Fresh conversations with selected non-conversation application data retained

Possible bounded extension if Francisco wants accounts/credits/model preferences/MCP/project settings to survive. Copy only an explicitly listed set with referential closure into the new app DB, preserve stable user identities or a reviewed mapping, preserve encryption key access without exposing values, and invalidate login sessions if the chosen auth deployment requires it. MCP OAuth callback URIs/issuer must remain valid or require reauthorization. Exclude project-chat links/documents/votes with legacy message dependencies. This is more operational work than A and should not be silently included in “fresh conversations.” Recommendation: A is default; choose B only for explicitly valued records, especially balances and connected accounts.

### C. Readable legacy archive or exact import (defer, not a gate)

A separate read-only legacy deployment can provide archive access against the old store, without exposing old mutation/worker endpoints. Exact Eve import would additionally require a corpus converter and proof for branch IDs, provider metadata, tool inputs/results, image bytes, document revisions and context loss. Current UI records + five-message transformations do not establish original exact model history. Never fabricate an exact provenance claim or re-run actions to fill holes. #292 does not require either feature, so do not spend migration critical path on it.

## Bounded PR slices and dependency edges for the parent plan

1. **Contract and fixtures, no engine switch:** fixtures from existing ChatJS paths/parallel tool outputs; durable identity/tree/execution contract and threat matrix; approved storage-owner boundary. Depends on refreshed Eve gap audit and existing thread contracts. Independent of legacy conversion and #328/#330.
2. **Application repository and authorization seam:** trusted Better Auth/anonymous callers, additive fresh schema definitions for node/binding/projection ownership, fail-closed raw-route guards. May run beside CLI/tool work after contract freeze. Does not require switching production reads/writes.
3. **Canonical history/creation integration:** exact selected Eve patch/fork/public API; durable reservation, canonical references, branch seed, compaction provenance and recovery tests. Depends on narrow upstream-gap proof; blocks full engine replacement.
4. **Feature persistence integration:** votes/projects/sharing/documents/files/credits/MCP service consumers updated to stable app node/effect references, each with bounded tests. Parallel ownership is safe only with a shared agreed node/effect interface; no duplicated authority. Integrate selected CLI source inventories without editing its active worktree.
5. **Cutover/rollback harness and docs:** disposable old/new store backup/restore and traffic-drain exercise, inventory/security checks and breaking-change notice. Can begin independently from contracts; release acceptance depends on full parity.
6. **Switch existing app and retire legacy execution code:** after parity gate, remove route streaming persistence/Redis resume/GenerationCancellation writes and obsolete projections only when no consumers remain. Preserve ordinary metadata APIs, unrelated cache/rate limiter, Files SDK, AI SDK feature calls and account integrations. Legacy release/data retention is operational, not permanent dual-engine source compatibility.

No schema migration must delete legacy production records during ordinary deployment. New fresh-store initialization and an explicit eventual archive disposal are different operations. No public fork, upstream submission, migration implementation, merge or deployment is authorized by this plan.

## Acceptance tests and release gates

Security/database tests should use real PostgreSQL and multiple independent gateway/worker processes where the invariant is distributed; browser tests protect routing/view semantics; deterministic models isolate workflow behavior, with at least one real configured provider flow separately.

| Invariant | Positive and negative proof |
| --- | --- |
| Owner/session isolation | Same owner create/send/replay/cancel/respond succeeds; wrong/missing issuer, subject, owner, origin and expired credential fail. Mixed conversation/session/turn/input/message IDs fail even if each exists. Bob cannot join Alice's concurrent create promise; repeated Alice operation returns same result. Test raw Eve stream/message/cancel/compact/clear/reset/subagent paths and callback ingress separately, not only tRPC. |
| Creation/recovery | Kill gateway at each reservation/create/binding boundary, retry concurrently from two replicas, require one canonical session or explicit unresolved state with no duplicate. Test eventual reconciliation separately; do not claim full recovery from safe refusal. Invalid preflight payload creates no stuck operation; valid unknown delivery retains exact payload. |
| Exact path execution | Historical edit/regenerate/parallel model responses seed exact selected prefix with completed tool and document refs; sibling remains intact; inherited external effect count stays one. Wrong-owner/missing/cyclic parent rejected. Long valid histories are not silently cut at 100. |
| Compaction/memory | Effective prefix reads exact committed canonical state; descendant can use applicable compacted memory; sibling/stale prefix cannot; original display messages/revisions remain intact. A browser cannot request raw privileged canonical history. |
| Replay/projection | Delete only derived projection and rebuild from authoritative facts without losing rich parts/tool output. Projection/event cursor crash windows cannot skip facts or duplicate messages. Unknown custom outputs fail at validation or render a defined fallback, never corrupt history. |
| View/execution lifetime | Switch panels while two runs continue; stop one; approve hidden originating execution; reload pending input and streaming state; no replacement create. Callback-only Eve send failures retain draft and require replay reconciliation before retry. |
| Domain effects | Duplicate replay cannot double-charge credits, duplicate revisions or repeat irreversible tool action. File references survive sibling deletion and archive retention. Vote/document/message IDs cannot cross authorized chat boundaries. Public sharing exposes only allowed display data; cloning creates authorized independent IDs/references without running old tools. |
| Host/World | Built selected Next/Eve deployment demonstrates actual World rows, worker callbacks and abrupt restart, not just HTTP health. Worker recovery never unlocks all jobs in a shared database. Duplicate continuation/session creation race tested at selected World boundary. |
| Upgrade/rollback | Resume representative suspended run under supported candidate tuple or prohibit mixed rollout and drain/isolate; restore old backup with old build and new backup with new build. Byte/object/encrypted connector access verified using test credentials without printing secrets. |
| Existing app and installation | Existing default configuration passes full browser feature ledger; Bun lint/types and relevant tests pass. Installed selected output inventories match CLI's resolved selection and external options; no standalone Eve-only example stands in for ChatJS. |

Material choices for review are limited to (1) default fresh account/application metadata reset versus explicit retained subset, (2) operational host/World recipe actually supported for the reference demo, and (3) acceptable recovery/upgrade envelope after the gap proofs. Fresh legacy conversation conversion is already resolved as unnecessary; existing branching semantics are already required. Implementation owners can decide routine table/index naming and source layout autonomously.
